# dsh-superagent 二次开发可行性评估与优化路线

> 评估对象：`deepseek-ai/dsh-superagent-prototype` @ `6337fc8`（研究原型，MIT）
> 评估方式：**本机真实部署 + 端到端跑通**后的代码走查，非文档推演
> 评估日期：2026-11-02 ｜ 配套文档：[windows-patches.md](windows-patches.md)

---

## 一、结论（一页）

**可行，且成本比预期低得多。**

关键事实是：**原型本身就是一个 DSH 插件（bundle）**，不是参考实现、不是需要重新实现的架构图。我们已在本机完成部署并跑通完整闭环——GitHub 评论 → 源轮询捕获 → 准入判定为显式请求 → 建工单 → 开启独立 worker 会话与独立工作目录 → 模型执行 → 在原会话回帖。

因此真正要回答的问题不是"能不能做"，而是"**以什么形态做**"：

| 路线 | 含义 | 成本 | 判断 |
| --- | --- | --- | --- |
| **A 接管式加固** | fork 原型，把它变成可长期依赖的产品（已有 7 处本地补丁 + 待补清单） | 中 | ✅ **推荐** |
| **B 伴生式扩展** | 原型不动，另写插件补能力（本地任务源、通知推送、面板增强） | 低–中 | ✅ 可行，但受限于原型的接口面 |
| **C 全量重写** | 只借鉴架构，自己实现全套 | 高 | ❌ 现在不成立：无证据支持重写优于加固 |

**推荐路线 A，并按"先能长期跑 → 再能自己触发 → 再能随宿主演进"三步推进。** 理由见 §四。

## 三、逐模块复用度评估

| 模块 | 上游实现 | 我们的实测结论 | 复用建议 |
| --- | --- | --- | --- |
| Sources（GitHub / 飞书） | 完整可用 | GitHub 源实测轮询、准入、投递正常 | **直接复用** |
| Core（Trigger / Thread / Ticket / Eval / Effect 队列） | 完整 | 工单状态机、准入矩阵、评估流程工作正常 | **直接复用** |
| Store（SQLite 持久化） | 完整 | 11 表 + 生成列 + 索引；重启后状态可恢复 | **直接复用** |
| Sessions / Executor | 需改 | 工具名写死 `bash`，本机宿主为 `pwsh` → 插件不激活 | 改为主动探测宿主能力 |
| Panel（6 页签） | 可用 | 渲染正常，缺"手动建单"入口 | **复用 + 补入口** |
| Deployment（进程托管） | 必须改 | 依赖 tmux（Windows 无）；强杀残留锁目录 | **重写这一层** |
| 环境与凭据层 | 必须改 | 路径校验、shim 可执行性、凭据隔离 | 已改 3 处（见补丁文档） |

**结论**：核心领域模型与调度逻辑**不需要重写**。真正要投入的是适配层与产品化补强。

## 四、真实技术债（部署期实测，逐条可复现）

| # | 问题 | 现象 | 根因 | 状态 |
| --- | --- | --- | --- | --- |
| 1 | 宿主契约漂移 | 本机 shell 工具叫 `pwsh`，原型写死 `bash`；`tools.restrict()` 拒绝未知工具名 → **插件完全不激活**，API 全 404 | 上游按旧版宿主写死工具名 | ✅ 已修 |
| 2 | Windows 路径假设 | `stateDir` 校验只认 `/` 开头 → 插件校验失败不激活 | POSIX 绝对路径假设 | ✅ 已修 |
| 3 | Windows shim 不可执行 | worker 的 `#!/bin/sh` shim 无扩展名，PowerShell/PATHEXT 看不见 | POSIX shim | ✅ 已修 |
| 4 | **删除 issue 打挂源** | 上游只认 HTTP 410；GitHub 对已删除 issue 返回 404 → 每轮轮询失败，源持续 `error` 达 24 小时 | 上游刻意保留 404（防止误判权限被撤销），但代价过大 | ✅ 已修（404 时复核仓库可读性） |
| 5 | 配置保存后路由 404 | 保存触发进程内重启，`/orchestrator/api/*` 路由不重新注册 → 必须重启整个 DSH 进程 | 热重载未重新注册路由 | ❌ 未修 |
| 6 | 单账号无法自触发 | 原型刻意跳过 agent 自己发布的内容（防自触发环）→ 只有你一个账号时**永远无法触发** | 设计假设"专用 agent 账号" | ✅ 已修（收窄放行） |
| 7 | 强杀残留 | `proper-lockfile` 锁目录 + 端口占用 → 下次启动失败 | 无优雅退出 | ✅ 已修（启停脚本清理） |
| 8 | 数据无回收 | `trigger` / `disposition` / `decision` 行无限增长 | 上游文档自陈"尚未删除任何记录" | ❌ 未修 |
| 9 | 触发源只有两个 | 无本地文件源、无 webhook、面板无手动建单 | 设计范围限定 | ❌ 未修（cookbook 有配方） |

**#4 与 #6 是本次部署亲手触发的**：前者由我删除测试 issue 触发，后者由"只用自己一个账号"触发。两者都不是阅读文档能发现的。

## 五、优化清单（按价值 ÷ 成本排序）

| 优先级 | 优化项 | 价值 | 成本 | 做法要点 |
| --- | --- | --- | --- | --- |
| **P0** | 本地目录源 | 高 | 低 | 按 `008-cookbook.md` 新增一个 Source kind：目录内的文件/待办即触发源 |
| **P0** | 简单 HTTP webhook 源 | 高 | 低 | 同上；让 IDE / CI / 脚本能主动派活 |
| **P0** | 面板手动建单 | 高 | 中 | 工单模型已在面板内，只缺入口；可顺带做"把本地任务变成工单" |
| **P0** | 进程守护 + 优雅退出 | 高 | 低 | 替代 tmux；Windows 服务或自监控 + 锁清理 + 端口回收 |
| **P0** | 配置热重载修复 | 中 | 中 | 让保存后不必重启整个 DSH 进程（技术债 #5） |
| **P0** | 一键诊断包 | 中 | 低 | 打包 log + runtime + settings + 版本信息；本次排查端口/锁/路由/工具名耗时很久 |
| **P1** | **能力探测层** | 高 | 中 | 不写死工具名与配置 schema，运行时向宿主探测；根治"DSH 一升级就炸"（技术债 #1 的通用解） |
| **P1** | 通知回路 | 高 | 中 | 工单完成/阻塞时主动推给使用者。注意：宿主 session 事件不可达，只能走轮询 + 面板 + 系统通知 |
| **P1** | 多仓支持 | 中 | 中 | 领域模型已按 repository 维度切分，主要是配置与面板的扩展 |
| **P1** | 第二个 agent 账号 | 中 | 低 | 让"外部请求者"路径可验证（当前单账号下被自过滤挡住） |
| **P2** | 数据保留策略 | 中 | 中 | SQLite 已有索引与生成列，补 GC 即可 |
| **P2** | 中文优先的界面与提示词 | 中 | 低 | locale 已含 zh/en，把默认值倾向中文 |

## 六、分阶段路线与验收标准

```mermaid
flowchart LR
  S1["阶段 1 · 能长期跑<br/>守护/热重载/诊断包"] --> S2["阶段 2 · 能自己触发<br/>本地源/webhook/手动建单"]
  S2 --> S3["阶段 3 · 随宿主演进<br/>能力探测/跨平台/多仓/回收"]
  S3 --> S4["阶段 4（可选）· 主动通知"]
```

### 阶段 1「能长期跑」（约 1 周）

范围：技术债 #5、#7，加诊断包。
**验收标准**：
1. 连续运行 7 天无需人工干预；
2. 修改任一配置项后无需重启 DSH 进程即可生效；
3. `status` 在任何状态下都不误报 error；
4. 一条命令产出可粘贴的诊断包（进程、端口、锁、路由注册、settings、log 尾部）。

### 阶段 2「能自己触发」（约 1 周）

范围：技术债 #6、#9，加本地源 / webhook 源 / 手动建单。
**验收标准**：
1. 在本地放一个文件 → 面板出现对应工单，全程不碰 GitHub；
2. 面板可手动创建工单并派发；
3. 单账号部署下，`@agent` 评论可触发（收窄放行不产生自触发环：agent 自己的回复不含 @）。

### 阶段 3「能随宿主演进」（约 1–2 周）

范围：技术债 #1、#8，加能力探测层与跨平台抽象。
**验收标准**：
1. 宿主小版本升级后，插件不因工具改名或配置 schema 变化而失效；
2. 旧版数据自动迁移，升级前有备份与回滚路径；
3. 触发、处置、决策三类记录有保留期，库体积不再单调增长。

### 阶段 4（可选）「通知到你面前」

工单完成 / 阻塞 / 需要决策时主动推送到当前 DSH 会话或系统通知。

## 七、风险与边界

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 研究原型定位 | README 自陈"research prototype, not production-ready"，可能含 bug、风格不一致 | 以阶段 1 的验收标准作为准入门槛；补丁集可重放，便于跟随上游 |
| 上游契约漂移 | 原型按 `engines.dsh ^0.2.1-alpha.2` 开发，本机为 `0.2.1-rc.5` | 阶段 3 的能力探测层；升级前跑本地补丁集 + 类型检查 + 构建 |
| 依赖宿主包 | 22 个 `@deepseek-ai/*` 依赖随宿主版本走 | fork 时锁定版本；不承诺独立于宿主运行 |
| 账号即身份 | agent 以你的账号发言、提交、开 PR | 先用专用账号再开 `auto`；observe 模式下显式请求仍会执行，需知悉 |
| 数据增长 | trigger/decision 无回收 | 阶段 3 的保留策略 |
| 权限边界 | worker 以你的 OS 用户运行，可读写家目录 | 每工单独立目录 + 独立 git 配置；敏感操作走面板确认 |

## 八、需要澄清的三个预期

用户此前那份《DeepSeek Super-agent 完整说明》里的三处说法与原型实际不符，以原型为准：

1. **面板没有"手动新建工单"**——任务必须由来源（GitHub / 飞书）驱动进入；
2. **没有"纯本地文件任务"这一档**——想本地起步需自行实现一个 Source（cookbook 有配方，约 300 行）；
3. **DSH 内没有 `/superagent` 斜杠命令**——它是常驻调度服务，入口在 Web 面板侧边栏。
